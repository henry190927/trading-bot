# 倉位與止盈單重構：開倉只設停損 + 一個止盈，之後自由加減分批止盈（草稿，待審）

> 狀態：**方向已核可（2026-10-25）**，第 6 節的決定已定案；依 (a)(b)(c) 三步實作。
> 目標：像正規交易所一樣——開倉只有兩個價位（停損、最終止盈），倉位建立後再自由加上
> TP1 / TP2 / TP3…，也可以移動最終止盈。

---

## 1. 現在的設計，以及它卡住的地方

journal 每一列有**固定兩個止盈欄位**，各自綁一套下單邏輯：

| 欄位 | 怎麼掛上交易所 | 何時 |
|---|---|---|
| `stop` | 附掛在進場單（`ATTACHED:<entryId>`） | 進場成交瞬間，交易所自動啟用 |
| `tp2` | 附掛在進場單，**觸發時平掉整個部位** | 同上 |
| `tp1` | 不能附掛（附掛的止盈會平 100%，跟分批衝突）→ web 每 30 秒巡檢，成交後補掛 reduce-only 限價單 | 成交後 0–30 秒 |

另外有 `tp1_auto` / `tp2_auto` / `stop_auto` 三個「要不要自動掛」的旗標、`tp1_order_id` / `tp2_order_id` 兩個單號欄位、
`tp1_fill_price` / `tp1_fill_pct` / `tp1_filled_at` 三個 TP1 成交欄位，R 用 `BlendedExit` 把 TP1 腿和剩餘部位合併。

**卡住的地方**
- **止盈數量寫死兩個。** 要 TP3 就得再加一整組欄位、旗標、巡檢邏輯、合併公式。
- **開倉後改不了止盈。** 編輯 journal 只改數字；系統看到單號已存在就拒絕重掛（「cancel on BingX first」）。
- **「計畫」和「實際掛單」混在同一個欄位。** `tp1` 同時是開倉時的計畫價、要掛的單、成交後的紀錄。
- **巡檢要負責補單。** TP1 延後補掛的機制，就是 #92 那次「瀏覽器沒開就沒掛」問題的來源（後來改成背景巡檢才解決）。

## 2. 新設計的核心原則

沿用 bracket guard 已經在用、而且驗證過的原則：

> **交易所是「現在掛著什麼單」的唯一真相；journal 只記「當初的決定」和「已經發生的成交」。**

| 資料 | 存在哪 | 理由 |
|---|---|---|
| 進場、停損（R 基準）、開倉時的最終止盈計畫 | journal | 這是決定，事後不該被改寫（停損是 R 基準，移動停損本來就不改它） |
| **現在掛著的** 停損 / 止盈單 | **不存**——每次即時向交易所查 | 存了就會跟交易所不一致（這次 #93、以前的裸倉，都是「journal 以為有、交易所沒有」） |
| **已經成交的** 分批出場 | journal（新的一欄，見 3.1） | R 要用，而且交易所的歷史只查得到 7 天 |
| 最終平倉 | journal（現有欄位） | 不變 |

這樣做之後，**單號欄位和「自動補掛」旗標都可以拿掉**：開倉時只附掛停損 + 最終止盈（交易所原生、成交瞬間生效），
其他止盈都是倉位建立後你手動加的，直接送到交易所，不需要巡檢延後補單。

## 3. 資料結構

### 3.1 journal 新增一欄 `exits`（分批出場紀錄）

一個 JSON 陣列，每筆是一次「已成交的部分平倉」：

```json
[{"price": 82.0, "qty": 50.0, "pct": 50, "at": "2026-10-21T23:00:00+08:00", "order_id": "2113...", "src": "exchange"}]
```

- `pct` 是佔**原始部位**的百分比（R 的權重要對原始部位算，才能跟其他交易比）。
- `src`：`exchange`（巡檢從成交紀錄抓到的）或 `manual`（你手動補的）。
- 最終平倉照舊寫在 `exit_price` / `closed_at`，但 `exit_price` 存**所有腿依數量加權的平均**——
  這是現在 `BlendedExit` 已經在用的技巧：R 對出場價是線性的，存加權平均之後，
  之後任何編輯觸發的 R 重算都還是對的（記憶裡「編輯會重算 R、分批的真實 R 會在第一次編輯時遺失」那個坑，靠這個避開）。

**R 的算法**（一般化現在的 TP1 公式）：

```
R = Σ (pct_i / 100) × R(price_i)  +  (1 − Σ pct_i / 100) × R(最終出場價)
```

### 3.2 拿掉或改名的欄位

| 現在 | 之後 |
|---|---|
| `tp2` | 改名語意為「**最終止盈**（開倉時的計畫）」，欄位名稱可保留以免動到 CSV 格式 |
| `tp1` | 只留給舊資料讀取；新交易不再寫 |
| `tp1_auto`、`tp2_auto`、`stop_auto` | 拿掉（開倉時勾的「附掛停損 / 附掛止盈」改成表單上的單次選項，不存） |
| `tp1_order_id`、`tp2_order_id`、`stop_order_id` | 拿掉（現在掛著什麼，問交易所） |
| `tp1_fill_price/pct/filled_at` | 轉進 `exits` 的第一筆 |

> 替代方案：不改 CSV，另開 `trade_events.jsonl` 存所有下單 / 改單 / 成交事件（event sourcing）。
> 優點是完整歷程可以重播，也正好是 Kafka 那份設計的好題材；缺點是 R 要從事件算出來，journal 不再自足，
> 而且多一個要備份、要對帳的檔案。**建議先用 `exits` 欄位**，事件檔等真的需要歷程時再加。

## 4. 使用流程

**開倉**（/journal/new、/chart 快速記錄）：進場價、停損、最終止盈三個價位 + 保證金、槓桿。停損和最終止盈附掛在進場單上。

**/today 持倉卡**（成交後）：

```
SUI 多 100x · #94                                      +0.42R
停損 ─────── 進場 ──●──── TP 0.935 ── TP 0.948(最終)
現在掛著:停損 0.9150 · 止盈 0.9350(30%)· 最終止盈 0.9480(剩餘全部)
[+ 加止盈]  [移動停損]  [移動最終止盈]  [取消某張止盈]  [平倉]
```

- **加止盈**：輸入價位 + 數量百分比 → 預覽（這張成交會鎖住多少 R、多少 u）→ 確認送出 reduce-only 限價單。可以加很多張。
- **移動最終止盈**：跟移動停損同一套兩步流程，先掛新的再取消舊的。
- **取消某張止盈**：列出交易所上現在掛著的止盈單，選一張取消。
- **分批成交**：巡檢從成交紀錄抓到部分平倉 → 寫進 `exits`（取代現在只認 TP1 單號的 `detectTP1Legs`）。
- **最終平倉**：方案 A 已上線的「依交易所成交平倉」，帶入時自動把已記錄的分批腿排除。

## 5. 要先確認的交易所行為（實作前驗證，不是假設）

1. **附掛的最終止盈，在部分平倉之後會平掉「剩下的」還是「原始數量」？**
   程式註解寫「附掛的停損 / 止盈會平 100% 部位」，推測是平剩餘部位，但沒驗證過。
   如果是原始數量，分批之後它可能被交易所拒絕或行為異常，最終止盈就得改成獨立的 reduce-only 單。
2. **附掛止盈的 orderId 怎麼找。** journal 現在只記進場單 id；移動最終止盈要先從掛單列表找出它（做法同移動停損找現有停損）。
3. **分批止盈要用限價單還是 TAKE_PROFIT_MARKET？** 限價單是 maker、手續費低，但可能「碰到沒成交」；
   觸發市價單一定成交但吃 taker 費和滑價。
4. **雙向持倉模式下 reduce-only 的參數**：程式裡已有註解，hedge mode 不能帶 `reduceOnly`，要用 positionSide——沿用現有的 `PlaceReduceOnlyLimit` 即可。

做法：用小資金（最低下單量）在交易所實測 1、2，結果寫回這份文件再開工。

## 6.1 原始的待決問題

1. **方向確認**：「現在掛著的單只問交易所、journal 只記決定和成交」這個原則，你同意嗎？（它會讓單號欄位和自動補掛全部消失）
2. **分批止盈的百分比**：以「原始部位」計（建議，R 才可比），還是以「當下剩餘部位」計（比較像交易所 App 的操作）？
   UI 可以兩種都顯示，但存檔要選一種。
3. **分批止盈的單別**：限價（建議，省手續費）還是觸發市價？
4. **舊資料**：已平倉的歷史列維持原樣唯讀（建議），還是全部轉成 `exits` 格式？目前開著的倉要等平倉後再切換。
5. **資料結構**：`exits` 欄位（建議）還是另開事件檔？
6. **先後順序**：建議分三步上線，每步都能單獨用：
   (a) 移動最終止盈 → (b) 加 / 取消分批止盈 + `exits` 自動記錄 → (c) 拿掉舊欄位和自動補掛。
7. **留白給你寫**：適合的片段有 N 腿 R 的計算函式、從成交紀錄辨識「部分平倉」的邏輯、
   移動最終止盈的「先掛新、再取消舊」流程（失敗時要怎麼回復）。
