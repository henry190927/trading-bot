> 起因:2026-10-10 OCI console 被 MFA 鎖死 + SSH 同時失效,無法存取生產機器。
> 真錢零曝險(無持倉、autotrade 未跑),唯一不可替代的損失是 `journal.csv`。

## 🔴 先釐清病因

**這不是儲存問題,是「單一存取路徑」問題。**

```
資料沒壞 · 機器沒死 · 磁碟沒爆 —— 東西全都好好的,只是碰不到
```

換資料庫、換 IPFS,今天的結果一模一樣。**搞錯病因會導致過度設計。**

## ① 資料耐久性 —— 三階段

> ### 🔑 判準:這次壞的是「存取」,不是「磁碟」
>
> ```
> 磁碟沒壞 · 機器沒死 · 資料沒損 —— 只是進不去
> ```
>
> **所以備份必須在 Oracle 之外。** 這一條直接淘汰最常被推薦的兩個選項:
>
> ```
> ❌ OCI Object Storage       同一個帳號,帳號鎖了一起鎖
> ❌ OCI Block Volume Backup  同上(原生、排程方便,但同帳號)
> ```
>
> **原生快照對「磁碟壞掉」有效,對「你被鎖在外面」完全無效。**

### 選項對照

| 方案 | 異地 | 版本史 | 加密 | 成本 | 備註 |
|---|---|---|---|---|---|
| **private git repo** | ✅ | ⭐ 完整 | 🔶 傳輸 | 免費 | 66KB CSV 的甜蜜點 |
| **rclone → R2 / B2** | ✅ | 🔶 需開版控 | ✅ | ~$0 | 通用,大檔也行 |
| **restic → B2** | ✅ | ✅ 快照 | ⭐ 端到端 | ~$0 | 正統備份,去重+保留策略 |
| Syncthing → Mac | ✅ | 🔶 | ✅ | 免費 | ⚠️ Mac 要開機 |
| cron + scp → Mac | ✅ | ❌ | ✅ | 免費 | ⚠️ 同上,且會覆蓋 |
| OCI Object Storage | ❌ | — | — | 免費 | **同帳號,不算備份** |
| OCI Volume Backup | ❌ | ✅ | ✅ | 免費額度 | **同帳號,不算備份** |

### 🟢 Phase 1 — private git repo(現在做,~30 分鐘)

**為什麼是 git**:不是因為它是備份工具,是因為資料剛好落在它的甜蜜點 ——
**小(66KB)· 純文字 · 變動不頻繁 · 需要歷史**。

⭐ 「需要歷史」這點最關鍵。對照既有筆記:

> 「儲存任一列會從 exit_price 重算 R,所以分批出場的 trade 在第一次編輯時
> 會失去真實 R(#53 損失 +0.44R)」

**有 git 才能 diff、才能還原、才能知道「這一列是什麼時候被改成這樣的」。**
其他備份只給你「某時間點的完整檔案」,給不了逐列的變更史。

```
□ 開 private repo:trading-bot-data
□ VPS 上產 deploy key(只給該 repo 寫入權,不要放個人 SSH 金鑰)
□ 一支 ~30 行腳本:cd → git add journal.csv → 有變更才 commit → push
□ cron 每日跑一次(或在 journal 寫入後觸發)
□ 失敗要有感:接 ntfy(既有的 NTFY_TOPIC)
□ ⭐ 還原演練一次 —— 「沒驗證過的退路等於沒有退路」
```

⚠️ repo 必須 **private**(交易紀錄是個資)

### 🔶 Phase 2 — SQLite + Event Sourcing(之後,1–2 天)

**要做,但理由不是備份。**

```
✅ 原子交易        不會寫到一半壞掉
✅ 查詢            不用整檔讀進記憶體
                   ← 對照筆記:「3.1MB 檔案每 request 重新解析 6 次」
✅ 明確 schema

❌ 不解決耐久性    換引擎 ≠ 多副本
```

#### ⭐ 同時要改資料模型 —— 這才是「編輯一列重算 R」的解法

既有筆記:

> 「儲存任一列會從 exit_price 重算 R,所以分批出場的 trade
> 在第一次編輯時會失去真實 R(#53 損失 +0.44R)」

**這是【可變狀態】的 bug,不是儲存引擎的 bug。** 現在存的是「交易的當前樣子」,
每次存檔重算一次 R —— 所以每一次編輯都在摧毀歷史。換成 SQLite 不會自己好。

**解法:存事件,不存狀態。**

```
events                               derived(算出來的,不存)
──────────────────────────────       ──────────────────────
#53 OPENED   qty 1.0 @ 2500          → 當前部位
#53 PARTIAL  qty 0.5 @ 2560          → 真實 R(從所有 leg 算)
#53 STOP_MOVED       @ 2520          → 當前停損
#53 CLOSED   qty 0.5 @ 2590          → 已實現損益
```

```
✅ R 從整串事件算出來 → 分批出場天然正確
✅ 編輯不可能破壞歷史 → 沒有「編輯」,只有「再追加一個事件」
✅ 改錯了補一筆 CORRECTED,原始紀錄永遠留著
✅ 任何時間點的狀態都能重播
```

**一張 `events` 表就夠。** 單一寫入者、單一機器,不需要任何訊息系統。

#### ❌ 為什麼不用 Kafka

```
① append-only 不能原地更新 → 要 log compaction + key,迂迴重做資料庫
② 運維重量不成比例 → broker 要 GB 級記憶體,為了 66KB
③ ⭐ Kafka 不是備份 → broker 在同一台機器,帳號鎖了一樣拿不到
                        跟「換資料庫」是同一個錯
④ 預設按時間/大小刪除,永久保存要反過來設定
```

**Kafka 解的是「多生產者 × 多消費者的解耦」。現在是一個 process 寫、一個 process 讀
—— 那是函式呼叫,不是訊息匯流排。**

真正該引入的時機:engine / monitor / web 拆成獨立服務,且都要吃同一份事件流;
或需要重播歷史行情餵回測。那時候 Kafka(或更輕的 NATS)才划算。

#### 📌 面試用(Cake JD 的 nice-to-have 第一條就是 Kafka/MQ)

> 「我的交易系統有個資料模型問題:journal 存的是可變狀態,每次編輯會重算 R,
> 所以分批出場的真實損益在第一次編輯時就失真了。
>
> 正確解法是 event sourcing —— 存事件不存狀態,R 從事件流推導。
> 但我**不會為此引入 Kafka**:單一寫入者、單一機器,一張 SQLite 的 events 表就夠。
> Kafka 解的是多生產者多消費者的解耦,我一個都沒有。
>
> 如果之後 engine / monitor / web 拆成獨立服務、都要吃同一份事件流,那時候才划算。」

⭐ **「知道什麼時候不該用」比「會用」更顯示資深度** —— 跟 K8s 那題同一個套路,
而且兩題都有真實的判斷依據,不是背來的。

### 🔵 Phase 3 — Litestream(SQLite 之後)

把 SQLite 的 WAL **持續複製**到物件儲存(R2 / B2):

```
每次寫入 → 幾秒內同步
可還原到任意時間點(PITR)
不需要 cron、不需要排程
```

**這才是「資料庫 + 備份」的正確組合 —— 備份能力來自 Litestream,不是來自 SQLite。**

```
□ litestream.yml → R2 或 B2(⚠️ 不要用 OCI,同帳號)
□ ⭐ 還原程序寫下來【並實測一次】
```

---

### ⭐ 三者不互相取代

遷到 SQLite + Litestream 之後,**git 那條不要拆掉**:

```
Litestream   給你 PITR —— 但你要【知道該還原到哪一刻】
git diff     給你逐列變更史 —— 一眼看出「這列被改成什麼」
```

對「編輯一列導致 R 失真」這種問題,**git 的 diff 比 PITR 更有用**。

→ 最終形態:**SQLite 當活庫 · Litestream 持續複製 · 每日匯出 CSV 進 git 留人看得懂的歷史。**
三件事各做一件別人做不到的事。

---

### 📌 為什麼公司可以「把資料放機器裡」而你不行

公司那樣做能成立,背後有一整套你沒有的東西:

```
Cloud SQL / 託管 DB   自動備份 + PITR,不靠人記得
磁碟快照排程          IaC 設定好,不是手動
⭐ IAM 多人管理        不會因為【一個人】掉了 MFA 就全組進不去
⭐ Terraform / IaC     機器掛了,重建是跑一支腳本
⭐ on-call 輪班        有人會在你睡著時發現異常
```

**2026-10-10 撞到的不是技術缺口,是「單人運維」缺口。**

公司用「人 + 流程」解決:多個管理員、交接文件、值班。
你只有一個人,**只能用自動化補**:

```
→ 備份必須【自動】      人會忘記,而且你忘了一年
→ 必須【異地】          你本人就是那個單點
→ 重建必須【便宜】      沒人能幫你手動重裝
```

> 這也是為什麼下面把「讓重建變便宜」排在「避免失去機器」前面。
> **公司不怕失去機器,因為重建是自動的。要的是同一個性質,不是同一套工具。**

## ② 部署與存取

### 這次暴露的

```
🔴 只有一把 SSH 金鑰,無備援
🔴 MFA 只綁一個 authenticator,無替代因素
🔴 沒有 bypass code
🔴 重建機器純手工 → 所以「失去機器」才這麼可怕
```

### ⭐ 最高價值的改動:讓重建變便宜

> **與其花力氣「避免失去機器」,不如讓「失去機器」不再是災難。**

```bash
scripts/provision.sh        # 全新 Ubuntu → 完整運作,目標 15 分鐘
  · 建使用者 + authorized_keys(⭐ 兩把金鑰)
  · 寫入 systemd units(trading-bot / trading-web / trading-monitor)
  · 從 git 拉 journal.csv
  · 帶 .env 上去
  · 啟動 + 驗證
```

**這支腳本本身就是災難復原計畫**,順便讓你隨時能換供應商。

### 立刻可做的三件小事

```
🔑 第二把 SSH 金鑰       不同機器產的,也放進 authorized_keys
🔑 MFA bypass code       重設成功後第一件事就產生並存進密碼管理器
🔑 驗證 serial console   ⭐ 在還能進去的時候先試一次
```

> **沒驗證過的退路等於沒有退路。** 這是本次最痛的教訓。

## ③ K8s

### 🔴 K8s 不適合這個系統

```
工作負載:  3 個 Go 靜態執行檔 · 1 台機器 · 單人使用
K8s 帶來:  control plane · etcd · CNI · Ingress · 大量 YAML

單節點叢集 = 多一整層會壞的東西,換來零個需要的功能
```

K8s 解的是「幾十個服務、自動擴縮、滾動更新、多人協作」—— 一個都不符合。

### ✅ 但 Docker 有實質好處

```
Docker    ⭐ 真的有用
  · 環境可重現 → 直接支援「重建要便宜」
  · 換供應商變成 docker compose up
  · Go 靜態連結 → 多階段建置 → FROM scratch,映像幾 MB

K8s       ⭐ 對職涯有用,對這個系統沒用
```

### 面試時的定位

> 「我把 trading-bot 容器化了,也寫了 K8s 部署清單並在 kind 上跑過。
> 但生產環境我刻意**沒有**上 K8s —— 單節點叢集對三個服務來說是淨成本。
> 那套清單的價值在於我理解 probe、resource limit、GOMEMLIMIT 在解什麼問題。」

**「知道什麼時候不該用」比「會用」更顯示判斷力。** 資深職缺的加分題。

獨家素材:**Go 靜態連結 → `FROM scratch`**,多數人只能講 Node/Python 的肥映像。
再加 `GOMEMLIMIT`(Go GC 看不到 cgroup limit,會被 OOMKilled)—— Go 專屬知識。
